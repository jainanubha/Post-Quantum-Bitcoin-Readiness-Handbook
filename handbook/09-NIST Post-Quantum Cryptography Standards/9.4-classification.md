# 9.4 Classification of post-quantum cryptographic standards

Cryptographic algorithms can be classified by the operation they perform and separately by the mathematical assumptions on which they rely. Conflating these dimensions can lead to misleading comparisons.

| Standard or candidate | Origin | Mathematical family | Function |
| --- | --- | --- | --- |
| FIPS 203: ML-KEM | CRYSTALS-Kyber | Module lattices | Key encapsulation |
| FIPS 204: ML-DSA | CRYSTALS-Dilithium | Module lattices | Digital signature |
| FIPS 205: SLH-DSA | SPHINCS+ | Hash-based | Digital signature |
| FN-DSA (FIPS 206 in development) | Falcon | NTRU lattices | Digital signature |
| HQC (selected for standardization) | HQC | Error-correcting codes | Key encapsulation |

## Key encapsulation versus signatures

A key-encapsulation mechanism (KEM) allows a sender and a recipient to obtain shared secret material. The public encapsulation key allows a sender to produce a ciphertext and a corresponding secret; the recipient uses the private decapsulation key to recover the secret. A separate symmetric cryptographic construction can then protect communication. A KEM by itself does not authenticate the identity of the peer.

A digital signature provides publicly checkable authorization or authenticity for a message relative to a verification key. A signer uses private material to produce a signature; a verifier checks it using the public key.

| Property | KEM | Digital signature |
| --- | --- | --- |
| Establishes shared secret material | Yes | No |
| Publicly verifies authorization | No | Yes |
| Encrypts application data by itself | No | No |
| Potentially replaces Bitcoin transaction signatures | No | Yes, after protocol integration |

## Implications for Bitcoin

ML-KEM and ML-DSA both use module-lattice mathematics, but ML-KEM cannot serve as a drop-in replacement for Schnorr or ECDSA. Bitcoin transaction validation needs public verification without a private decapsulation key. A KEM could instead be studied for communication protocols used by nodes, wallets or signing services. Conversely, a post-quantum signature standard is not an existing Bitcoin spending mechanism. A consensus design would need to specify how keys are committed to, what transaction message is signed, how signatures are encoded, and how verification costs are bounded.
