# 9.12 Comparative analysis and Bitcoin relevance

NIST standardization provides a basis for evaluating cryptographic primitives. Bitcoin introduces a different set of requirements because transaction verification is public, replicated and performed under adversarial conditions.

| Primitive | Function | Status (02-11-2026) | Initial Bitcoin research focus |
| --- | --- | --- | --- |
| ML-KEM | Key encapsulation | Final FIPS 203 | Off-chain communication and transport |
| ML-DSA | Digital signature | Final FIPS 204 | Public-key and signature size; verification cost |
| SLH-DSA | Digital signature | Final FIPS 205 | Large signatures; assumption diversity |
| Falcon / FN-DSA | Digital signature | Standardization ongoing | Compactness; signing implementation complexity |

## A proposed four-level readiness framework

This is a working analytical framework for the handbook, not a NIST classification or a claim that an algorithm has passed any particular level.

1. **Cryptographic readiness:** Is there credible analysis of unforgeability or key-establishment security under the relevant classical and quantum attack models?
2. **Specification readiness:** Are algorithms, parameter sets, encodings, failure conditions and test vectors clearly defined and stable?
3. **Implementation readiness:** Can independent implementations interoperate securely? Are signing devices protected against leakage and faults, and are verifier resource requirements understood?
4. **Bitcoin protocol readiness:** Can a specific spending mechanism be integrated with precise consensus behavior, acceptable validation costs, compatible wallet workflows and a feasible migration path?

A standardized algorithm may still require considerable work on implementation and protocol design.

## Bitcoin-specific evaluation dimensions

Public keys and signatures contribute to transaction data according to their placement and encoding. A future proposal must specify whether a key is exposed directly or committed to and revealed when spending. BIP141's witness accounting illustrates why raw signature bytes cannot be treated as a complete transaction fee estimate. Existing Script rules, witness element constraints and validation budgets must be analyzed for the actual proposed spending mechanism. Validation cost should be studied both for normal signatures and adversarial inputs. Wallet evaluation should include backup and restoration, hardware signers, multi-party authorization and key reuse. Migration must also account for existing outputs whose spending conditions are already fixed.
