# 9.9 FIPS 205: SLH-DSA

SLH-DSA is a stateless hash-based signature scheme derived from SPHINCS+. It provides an alternative to lattice-based signatures and uses hash-based components to build a reusable signing interface without a persistent signing counter.

## Building blocks and operation

The private key consists of secret seed material, a pseudorandom-function key, a public seed and a public root. The public key contains the public seed and root. A signature combines several components:

- A randomization value is derived during signing and included in the signature.
- A hash of message-related inputs determines the FORS message and the tree and leaf indices.
- FORS signs its portion of the digest by revealing selected secret values with authentication paths.
- A hypertree authenticates the resulting FORS public key through WOTS+ signatures and Merkle authentication paths at successive layers.

Verification reconstructs the FORS public key, then the successive tree roots, and compares the final root with the public key. These steps are conceptual; the exact address formats, hash inputs and encodings are defined by FIPS 205.

## Parameter sets

Each profile below represents two distinct standardized variants, one using SHA2 and one using SHAKE. The `s` profile prioritizes smaller signatures; the `f` profile prioritizes faster signature generation. All sizes are encoded bytes.

| Profiles (SHA2 / SHAKE) | Category | Public key | Private key | Signature |
| --- | ---: | ---: | ---: | ---: |
| 128s | 1 | 32 | 64 | 7,856 |
| 128f | 1 | 32 | 64 | 17,088 |
| 192s | 3 | 48 | 96 | 16,224 |
| 192f | 3 | 48 | 96 | 35,664 |
| 256s | 5 | 64 | 128 | 29,792 |
| 256f | 5 | 64 | 128 | 49,856 |

Source: FIPS 205, section 11, table 2 (public keys and signatures); private key length is four times the parameter $n$ in bytes. The names of the actual variants take the form `SLH-DSA-SHA2-128s` or `SLH-DSA-SHAKE-128s`, and so on. The standard's security claims are for defined signing volumes and security properties, not arbitrary unlimited use.

## Security and performance

SLH-DSA's small public keys are attractive for key storage and commitments, while authentication paths and intermediate signatures contribute substantial signature overhead. The time needed to sign and verify depends on the profile, hash implementation and hardware. A size table alone cannot establish which profile is most efficient for a validating node. Besides unforgeability, an application may require additional properties, such as message binding. FIPS 205 section 11 discusses this distinction. A Bitcoin integration must examine which properties are required by the intended spending construction and associated protocols.

## Limited-use parameters and Bitcoin

NIST's initial public draft SP 800-230 (April 2026) explores additional parameter sets for applications that limit the number of signatures per key. This work is particularly relevant to investigating UTXO-specific spending mechanisms. It is not part of the finalized parameter table above, and should not be treated as an approved new parameter set while the publication remains a draft.

A UTXO can be consumed only once on a particular valid chain, but signing is an off-chain event. A wallet may sign different fee-bumped transactions, generate alternative recovery transactions or reuse a key across multiple outputs. Even a key dedicated to one UTXO can generate several signatures. A limited-use scheme needs an explicit key lifecycle and signing policy rather than a simple assumption that one UTXO means one signature.
