# 9.3 Understanding NIST security categories

## Reference problems

NIST uses five security categories to compare the resources needed to attack a submitted parameter set with the resources needed to solve reference cryptographic problems. This approach avoids assuming that all classical and quantum attacks can be reduced to a single bit-security number.

| Category | Reference problem |
| --- | --- |
| 1 | Key search against AES-128 |
| 2 | Collision search against SHA-256 or SHA3-256 |
| 3 | Key search against AES-192 |
| 4 | Collision search against SHA-384 or SHA3-384 |
| 5 | Key search against AES-256 |

The reference is a comparison of attack resources under relevant computational models. Gate counts, circuit depth, available memory, parallelism and query assumptions affect these estimates. A category number is neither a literal number of quantum security bits nor a forecast of how long an attack will take.

## Hash security and quantum search

For an ideal $n$-bit hash, generic classical preimage search requires work on the order of $2^n$, whereas classical collision search takes roughly $2^{n/2}$ evaluations. Idealized Grover search reduces the query complexity of finding a preimage to the order of $2^{n/2}$. These expressions are not complete resource estimates for actual hardware. Collision finding is a distinct task and should not be modeled simply by applying Grover's algorithm to the classical birthday bound.

## Interpreting categories for Bitcoin

Under classical generic attacks, secp256k1 is commonly described as offering approximately 128-bit security against discrete logarithm recovery. That characterization is not a NIST PQC Category 1 rating: the curve is vulnerable to Shor's algorithm on an adequate quantum computer. Nor does the 256-bit length of a Schnorr public key imply 256 bits of security.

The intended security property matters. Transaction authorization primarily needs resistance to unauthorized signature generation. Other properties, such as binding a particular signature to a unique message or public key, may matter for particular protocols and must be evaluated independently. Selecting a category for Bitcoin requires studying output lifetimes, the number of keys targeted by an adversary, expected signing volumes, the possibility of changing algorithms in the future, and the cost of verification and on-chain data. This handbook does not prescribe a category for future consensus rules.
