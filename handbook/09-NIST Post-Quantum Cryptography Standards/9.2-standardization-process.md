# 9.2 Evolution of the NIST PQC standardization process

## Historical background

NIST began its public PQC selection process in December 2016. Rather than selecting algorithms solely on theoretical grounds, it invited submissions and exposed them to several rounds of security review, implementation studies and public discussion. The resulting portfolio reflects both practical performance and the value of maintaining alternatives founded on different mathematical assumptions.

| Year | Development |
| --- | --- |
| 2016 | NIST issues its call for proposals. |  
| 2017 | First-round candidates enter public evaluation. |
| 2019 | Second-round candidates are announced. |
| 2020 | Third-round evaluation begins. |
| 2022 | Kyber, Dilithium, Falcon and SPHINCS+ are selected for standardization. |
| 2024 | FIPS 203, 204 and 205 are finalized on August 13. |
| 2025 | HQC is selected as an additional key-encapsulation mechanism. |
| 2026 | Additional signature evaluation and limited-signature parameter research continue. |

## Evaluation criteria

Security is the first consideration, but a usable primitive must also be efficient and implementable. Relevant dimensions include resistance to known attacks, key and signature sizes, execution time, memory use, implementation complexity, licensing and flexibility across platforms. Public cryptanalysis helps uncover weaknesses that may not be evident from an initial security argument. The standards distinguish the algorithm from its parameter sets. A parameter set fixes choices such as dimensions, modulus, hash instantiation and security-related bounds. Consequently, an evaluation should identify the exact variant instead of referring only to the algorithm family.

## Why several schemes?

ML-DSA and SLH-DSA address the same broad functionality but rely on different constructions. Maintaining alternatives reduces dependence on any single class of hardness assumptions. It does not guarantee that failures will be independent, nor does it imply that all standardized schemes should be deployed together.

Bitcoin's requirements differ from NIST's general-purpose evaluation. A full node verifies transactions from potentially adversarial peers, often without knowing the signer. Global validation and replicated storage amplify resource costs. A candidate that is efficient for a conventional client-server application may impose undesirable costs when used as a consensus primitive. The NIST process provides valuable evidence but cannot settle those protocol-level trade-offs.
