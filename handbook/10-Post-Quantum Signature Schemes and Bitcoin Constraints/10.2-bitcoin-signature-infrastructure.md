# 10.2 Bitcoin's existing signature infrastructure

A comparison of post-quantum signatures requires a functional baseline. Chapter 03 covers the underlying elliptic-curve cryptography; here the focus is what current signatures enable within Bitcoin and what an alternative would need to preserve or redesign.

## Classical baseline

| Property | ECDSA (secp256k1) | BIP340 Schnorr |
| --- | --- | --- |
| Typical compressed public key | 33 bytes | 32-byte x-only public key |
| Raw signature encoding | DER, variable length (up to 72 bytes under strict DER) | Fixed 64 bytes |
| Transaction signature encoding | DER plus sighash byte | 64 bytes for default sighash; 65 bytes with an explicit permitted non-default sighash |
| Mathematical basis | Elliptic-curve discrete logarithm | Elliptic-curve discrete logarithm |
| Multiparty signing | Scheme-specific protocols exist | MuSig2 and other Schnorr-based protocols |
| Batch verification | Conventional encoding does not provide the same straightforward benefit | Batch verification described in BIP340 |
| Resistance to a sufficiently capable Shor attack | No | No |

Uncompressed ECDSA public keys exist in legacy contexts; the table gives the compressed baseline. BIP340's x-only encoding and BIP341's transaction signature format must not be conflated. Neither the raw signature length nor the public-key length is a complete input size.

## Signature messages and authorization

A transaction signature is meaningful only when bound to the correct message. Bitcoin's different script versions define which transaction fields are committed to through their signature hashing rules. A replacement signature scheme must therefore define the message or prehash interface, context separation, supported sighash modes and treatment of invalid encodings. Simply signing an arbitrary transaction identifier is not a substitute for these rules.

## Algebraic capabilities

The linear verification relation for Schnorr signatures has the schematic form

$$
sG=R+eP,
$$

where $G$ is the generator, $P$ the public key, $R$ the nonce commitment and $e$ a challenge derived from the signing transcript. Actual BIP340 verification additionally specifies encoding, parity and challenge rules. This structure supports carefully designed multiparty protocols and public-key tweaks. BIP327 MuSig2 combines participants' keys and signing contributions into a BIP340-compatible signature. Taproot commits to an optional script tree by tweaking an internal key. These features require their own security arguments; naive addition of public keys or partial signatures is not sufficient to prevent rogue-key attacks or nonce misuse.

## Replacement versus redesign

Independent signature verification can conceptually be added for a different primitive, subject to new consensus rules. By contrast, key tweaking, public child derivation, adaptor signatures, threshold signing and aggregation may require new scheme-specific constructions. A replacement need not replicate all classical features to be useful, but its missing capabilities must be explicit. Batch verification is an algorithmic opportunity, not an assertion that Bitcoin Core currently uses it for every spend.
