# 10.3 Evaluation framework for post-quantum signatures

Section 9.12 proposed four levels of readiness: cryptographic, specification, implementation and Bitcoin protocol readiness. This section turns those levels into an assessment procedure.

## Evaluation dimensions

| Dimension | Evidence to collect |
| --- | --- |
| Security | Formal security model, assumptions, parameter rationale, classical and quantum cryptanalysis |
| Specification | Exact algorithms, versions, encodings, error handling, test vectors and errata |
| Data efficiency | Public key, signature, commitment and proof lengths under a defined spending construction |
| Computation | Key generation, signing, valid and invalid verification costs |
| Memory | Peak allocation, stack use and working memory on relevant devices |
| Consensus safety | Deterministic parsing and validation, implementation interoperability |
| Resource security | Upper bounds on adversarial validation work, CPU and memory accounting |
| Composability | Multiparty signing, tweaking, aggregation and other protocol-specific properties |
| Wallet operation | Derivation, state, backups, recovery, interoperability and hardware constraints |
| Privacy | Disclosure of signing policy, public keys, participant information or signing state |
| Maturity | Standardization status, independent analysis and audited implementations |
| Upgradeability | Commitment to algorithm identifiers, migration paths and future compatibility |

## Security beyond basic unforgeability

Existential unforgeability under chosen-message attack (EUF-CMA) means that an attacker with access to signatures cannot produce a valid signature on a new message under the target key. Strong unforgeability (SUF-CMA) additionally considers producing a new valid signature for an already signed message. These notions are not interchangeable with every form of transaction or witness malleability.

The applicable construction may also need message binding, key binding, protection against related-key attacks, or security under concurrent multiparty sessions. Security proofs in the quantum random oracle model address adversaries able to make quantum queries to an idealized hash oracle. They should not be read as unconditional guarantees for concrete implementations.

Bitcoin has a large population of public keys and potentially very long asset lifetimes. Multi-user or multi-target attack costs, time available to the attacker, and the exposure of public keys should be recorded separately from a scheme's NIST security category.

## Assessment procedure

1. Identify the precise scheme, revision, parameter set and intended spending policy.
2. Define the security goal and adversary, including signing queries, key exposure, signing volume and quantum resources.
3. Check the specification and known cryptanalysis; mark gaps rather than assigning unsupported scores.
4. Identify consensus changes and resource limits needed for the spending construction.
5. Collect compatible benchmark and implementation evidence; evaluate wallet and recovery assumptions.
6. Compare candidates against the use case, documenting residual uncertainty and conditions under which a conclusion would change.

Use evidence states such as `specified`, `measured`, `research-only`, `unknown` and `not applicable`. A final FIPS publication establishes specification maturity; it does not establish Bitcoin protocol readiness.
