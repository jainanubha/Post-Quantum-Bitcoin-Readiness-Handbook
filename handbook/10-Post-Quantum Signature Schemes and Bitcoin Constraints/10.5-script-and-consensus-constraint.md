# 10.5 Bitcoin Script and consensus constraints

A signature algorithm cannot be used for Bitcoin spending merely because a library implements it. A consensus proposal must define how the algorithm is invoked, how its data is encoded, and how every validating node reaches the same result for every possible input.

## Existing constraints

| Constraint | Existing context | Question for PQ integration |
| --- | --- | --- |
| Stack element size | Ordinary executed tapscript stack elements are limited to 520 bytes | How will larger keys and signatures be represented? |
| Stack and altstack | Tapscript limits the combined number of elements to 1,000 | What temporary data and stack behavior are needed? |
| Signature opcodes | Tapscript defines `OP_CHECKSIG`, `OP_CHECKSIGVERIFY`, `OP_CHECKSIGADD` with BIP340 semantics for 32-byte keys | Which algorithm identifier and validation rules will be used? |
| Validation budget | Tapscript charges 50 units for signature operations with non-empty signatures, from a budget based on witness serialization size plus 50 | Does this accounting adequately bound new computational costs? |
| Witness serialization | SegWit defines serialized witness elements and block weight accounting | How is each key, signature and proof carried? |
| Sighash | Signature messages are version-specific | How are transaction fields and algorithm context bound? |
| Relay policy | Standardness is distinct from consensus validity | Can wallets and miners relay and include the new transactions? |

The 520-byte limit is not a limit on the total witness size or a universal limit on every witness item. For example, the tapscript and control block are separate from its initial execution stack. A 2,420-byte ML-DSA-44 signature cannot be placed as one ordinary executed stack element under the existing rules. Splitting it into smaller pieces does not solve the problem unless a new verification mechanism defines how those pieces are consumed and validated.

## Upgrade design space

BIP342 includes unknown public-key types intended to permit future soft-fork restrictions. Under current rules, a nonempty signature with a nonempty unknown-type key is treated as successful, subject to other applicable rules; this does **not** provide secure post-quantum authorization today. New semantics would need to constrain such spends and resolve size limitations. Similarly, upgrade hooks such as new script leaf versions, new witness versions or repurposed `OP_SUCCESSx` opcodes may offer different design options. An upgrade mechanism is not an implementation of a signature scheme, and spending via unassigned semantics should not be treated as safe.

## Consensus specification requirements

A proposal must specify canonical or otherwise unambiguous accepted encodings, algorithm and parameter identifiers, exact signature-message construction, valid key representations, invalid-input behavior, maximum resource costs and activation semantics. It must address edge cases such as truncated or oversized data, unsupported modes and arithmetic boundaries. Independent implementations need consistent acceptance results; signing can use randomized or hedged procedures without making verification nondeterministic.

The existing BIP342 budget should not simply be reused on the assumption that verification cost scales with signature size. An expensive signature could fit within the block-weight limit yet consume excessive CPU or memory. Conversely, charging a large fixed fee for a cheap operation could waste capacity. Resource accounting must be justified with a conservative bound for the proposed algorithm.
