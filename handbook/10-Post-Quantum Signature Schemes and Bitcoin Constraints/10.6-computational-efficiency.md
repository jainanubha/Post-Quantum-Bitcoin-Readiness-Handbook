# 10.6 Computational efficiency and verification costs

Signature size is visible on-chain, but computational cost is equally relevant to decentralization. Signing is usually performed by the owner or a designated signer; validation is repeated by independent nodes and may occur during transaction relay, block processing, or historical validation. Actual verification frequency depends on caches, node settings and validation paths.

## Operations and resource costs

| Operation | Relevant environment | Measurements |
| --- | --- | --- |
| Key generation | Wallet, signing device | Latency, entropy, memory |
| Signing | Hardware or software wallet | Latency distribution, retries, peak memory |
| Valid signature verification | Full node, miner | Latency, throughput, peak memory |
| Invalid signature verification | Full node under adversarial load | Worst observed cost, rejection behavior |
| Batch verification | Candidate verifier, if supported | Batch size, speed-up, fallback cost |
| Parsing and allocation | Transaction validation | Maximum input size, copies, temporary buffers |

ML-DSA uses rejection sampling during signing; Falcon's signer involves different sampling and numerical considerations. Hash-based schemes involve many hash computations. These observations alone do not establish which scheme is fastest. Optimized vector instructions, platform-specific implementations and parameter choices can alter results substantially.

## A proposed measurement protocol

For each published benchmark or future experiment, record:

- Scheme, exact parameter set, specification revision and signature encoding.
- Implementation repository and commit, build configuration, compiler, optimization flags and enabled instruction sets.
- CPU, RAM, operating system and device class; distinguish desktop, low-power node and hardware signer.
- Message size, interface (pure or prehash), measurement count, warm-up, timing method and cache assumptions.
- Median and tail latency, throughput and peak memory; record whether allocations and parsing are included.
- Input classes: valid, invalid but well-formed, malformed and boundary-length inputs.
- For randomized or rejection-based signing, the observed latency distribution and applicable failure behavior.

Measurements from different environments should be presented separately, unless a defensible normalization method exists. A benchmark is evidence for a specific implementation, not a universal upper bound for all implementations.

## Resource accounting and denial-of-service resistance

If a candidate spending construction allows $n$ verification operations and each has an independently established upper bound $t_{\max}$ under a stated implementation model, a simplified estimate of verification work is $n t_{\max}$. Parsing, memory allocation, hashing, batch-failure fallback and other script work must be considered separately. In practice, a consensus rule cannot enforce a device-specific time measurement directly; it can constrain deterministic proxies such as operation counts and input sizes, with budgets calibrated against conservative engineering evidence.

A fast average verifier may still have costly malformed-input cases. Batch verification may save work on valid inputs but require individual checks when a batch fails. Security analysis must consider the worst permitted transaction or block, not only ordinary wallet behavior.

## First-iteration status

No benchmark results are claimed in this chapter. Future work should compare reproducible measurements on a common set of hardware and evaluate bounded adversarial cases before proposing resource-accounting rules.
