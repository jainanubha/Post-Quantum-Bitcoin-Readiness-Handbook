# 10.11 Wallet and implementation constraints

Standardizing a signature and specifying its consensus validation rules do not guarantee that users can securely receive, hold and spend Bitcoin using the new construction. Wallet requirements must be investigated independently of the cost of full-node verification. This section defines engineering questions; practical readiness checklists belong to the later wallet chapter.

## Wallet lifecycle requirements

| Stage | Evidence and questions |
| --- | --- |
| Key creation | Entropy source, seed expansion, parameter selection and domain separation |
| Derivation | Hardened and public derivation semantics; algorithm-specific child keys |
| Receiving | Address or descriptor representation and discovery of compatible spending conditions |
| Signing | Exact digest, context, signing state, approval flow and device performance |
| Coordination | PSBT fields, parameter identifiers, key commitments and partial-signature formats |
| Backup | Seed versus expanded key encoding; durable mutable state when applicable |
| Recovery | Restoration from old backups, replacement of devices and fallback spending paths |
| Upgrade | Compatibility across wallet versions and migration of existing coins |

A short seed may regenerate a key pair even where an expanded encoded private key is large. Conversely, a compact seed backup alone may be insufficient for a stateful signature scheme if the wallet cannot safely reconstruct which signing indices have been consumed. Storage figures must distinguish seed, expanded key, cached data and mutable state.

## Hardware and offline signing

Hardware wallets operate with finite RAM, flash and processing power. An assessment should measure signing time, peak memory, random-number requirements and secure handling of private material. Larger keys, signatures and partial transactions may increase the number of QR frames or the size of USB, NFC or file transfers. Firmware must display the actual transaction intent and reject unsupported algorithm identifiers or signing modes rather than silently substituting a different policy.

ML-DSA's rejection sampling and Falcon's sampling strategy illustrate why signing-side implementation security requires its own analysis. Timing, power analysis and fault attacks may threaten secret keys independently of the security of the mathematical primitive. Countermeasures must be tested; constant-time behavior cannot be inferred merely from a language choice or a standard publication.

## Interoperability and failure behavior

A future PSBT extension would need to communicate relevant PQ keys, signatures, commitments and algorithm parameters in an unambiguous way. Existing BIP174 and BIP370 provide an extensible coordination format, but do not by themselves define PQ signature fields. A watch-only wallet, coordinator and signing device must agree on the transaction and its spending policy. Test vectors should include malformed data, unsupported parameters, interrupted signing, stale backups and device disagreement.

For stateful schemes, a signer should reserve and persist state safely before releasing a signature according to the scheme's specified lifecycle. A failed broadcast or transaction replacement must not automatically recycle state. A recovery path needs a clear policy for uncertain or corrupted state.

## Research questions

How would a hardware wallet securely sign and transport a large PQ signature? Can public-only wallet discovery be preserved without relying on elliptic-curve assumptions? What metadata is required for interoperable multiparty signing and backup restoration? Which failures could cause permanent loss rather than simply a rejected transaction?
