# 13.12 Wallet, exchange and custodian implications

## Readiness before migration

Operational adoption must precede reliance on a new output format. Wallets should be able to construct valid spending policies, back up relevant key and script material, and verify destinations under activated rules. Exchanges need both receiving and sending support; custodians must preserve multi-party authorization and withdrawal controls.

| Stakeholder | Key readiness requirement |
| --- | --- |
| Individual holder | Understand output exposure, backup coverage and migration fees |
| Wallet developer | Define derivation, descriptors, address validation, change and signing workflows |
| Hardware signer | Support reviewed signature algorithms and safe key generation |
| Exchange | Coordinate deposits, withdrawals, address support and service announcements |
| Custodian | Inventory policies, update distributed signing and test recovery procedures |
| Miner / node operator | Validate new consensus rules and resource requirements |
| Lightning or contract operator | Assess presigned transactions, channels and protocol-specific cryptographic dependencies |

## Inventory and data handling

A migration inventory should record script family, known exposure, signing mechanism, backup availability, whether independent recovery evidence might exist, and an estimated transaction size. It should avoid exporting real seed phrases or private keys to analysis tools. Public descriptors and extended public keys may disclose otherwise hidden authorization information; inventory design must treat them appropriately. Wallet derivation metadata and signing-policy information can be critical to later recovery even when the seed remains available.

## Operational phases

Before Phase A, support compatible destinations and safe change, identify outputs whose owner must be contacted and estimate migration demand. If Phase A were activated, a legacy-only receive workflow could become incompatible with the new restrictions. If Phase B were activated, any remaining legacy authorization would need to satisfy the actually deployed rescue conditions; backup possession alone would not guarantee this.

An institution may need approval from several parties before migration. Hardware firmware, watch-only servers, PSBT processing and audit records must remain interoperable. The transition may affect open Lightning channels and pre-authorized contractual transactions whose original spending policies cannot be replaced by a unilateral software update.

## Safety and communication

A research handbook should distinguish deployment readiness from a published proposal. Do not encourage real funds to be sent to a proposed witness format before its authorization is enforced. Communicate uncertainty around activation and quantum capability. Ensure that any future recovery service never requires users to disclose seed material to an untrusted party. Report migration completion as confirmed outputs protected by the intended policy, not merely as wallets that have installed software.
