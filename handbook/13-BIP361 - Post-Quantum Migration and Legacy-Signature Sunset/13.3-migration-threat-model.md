# 13.3 Migration threat model

## Adversary capabilities

The threat model extends Chapters 06–08. Assume an adversary observes the public chain and unconfirmed transactions. In stronger scenarios it also knows disclosed descriptors, extended public keys and previously published scripts. A cryptographically relevant quantum computer (CRQC) could solve the secp256k1 discrete logarithm problem for an exposed public key.

| Scenario | Attacker assumption | Main concern |
| --- | --- | --- |
| Classical baseline | No practical quantum key recovery | Ordinary wallet and protocol security |
| Long-exposure capability | Key recovery feasible over a long interval | Outputs with persistent or previously disclosed public keys |
| Short-exposure capability | Key recovery feasible during transaction confirmation | Competing spends when a hidden key is revealed |
| Stronger cryptanalytic scenario | Additional primitives or recovery assumptions fail | Re-evaluation of the proposed migration mechanism |

These are capability scenarios, not successive dates. A user may disclose a key off-chain before any on-chain evidence appears. A quantum adversary may recover a key without broadcasting a spend immediately, absence of observed theft is therefore not a proof of safety.

## Exposure window and transaction inclusion

Let $t_e$ denote the time at which a relevant public key becomes known to an attacker, and $t_c$ the time at which the legitimate migration is confirmed. A simplified exposure interval is $\Delta t=t_c-t_e$. If an attacker needs $T_Q$ for key recovery, the inequality $T_Q<\Delta t$ identifies an opportunity in this simplified model, not a guarantee of success. A competing spend still needs to satisfy the spending conditions and be included in a valid block. Propagation, fee policy, miners, confirmations and reorganization risk complicate the comparison. Ten minutes is an average block interval, not a guaranteed window.

For an old P2TR output the relevant output key is exposed at creation. For a fresh P2WPKH output its public key is normally revealed in the spending witness, unless it was disclosed earlier. A hash-hidden script may contain multiple conditions; whether an adversary can satisfy a complete path is a separate question. The proposed P2MR construction removes the exposed output key but can reveal classical leaf keys during a spend.

## Migration-specific failure modes

| Failure mode | Why it matters |
| --- | --- |
| Migrating after long exposure | The legacy key might already be compromised |
| Revealing a hidden key during migration | A sufficiently fast attacker could contest the spend |
| Selecting a weak fallback in a new output | A strong PQ path does not compensate for an independently usable weak path |
| Using an unactivated witness version | Existing nodes do not enforce the proposed authorization |
| Loss of backup or derivation metadata | A later rescue mechanism may be inaccessible to the holder |
| Incomplete validation upgrade | Older nodes may accept transactions invalid under new rules |

## What a deadline can and cannot achieve

A scheduled sunset can motivate earlier action and eventually remove some legacy spending opportunities. It does not secure the migration transaction before the new restrictions apply. Conversely, a new rescue rule can reduce some theft opportunities after activation but may exclude users lacking the required evidence. The transition requires protection of both the destination and the process by which it is reached.
