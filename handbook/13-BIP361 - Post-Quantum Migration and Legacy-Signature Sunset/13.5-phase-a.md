# 13.5 Phase A — Restricting quantum-vulnerable outputs

## What the draft proposes

Phase A seeks to stop creation of new outputs that continue to rely on vulnerable authorization. The specification table describes permitted legacy-to-PQ migration at 160,000 blocks after activation. The abstract frames the rule as a restriction on sending to vulnerable destinations. The draft is not detailed enough to derive a complete transaction classifier, including all mixed-input, change and non-payment outputs. This is a proposed consensus restriction, not merely a recommendation to wallet developers or a relay-policy setting. A receiving service that has not adopted a suitable output type could find itself unable to receive payments once such restrictions apply. The old coins are not automatically converted: before Phase B, they would still need to be spent into eligible destinations under the applicable rules.

## Conceptual model of destination eligibility

For an educational abstraction, let $A(o)$ denote whether an output $o$ satisfies a future Phase A destination policy. A simple payment-only transaction might be constrained by

$$\bigwedge_{o\in O_{\mathrm{payment}}} A(o)=\mathrm{true}.$$

This is not the BIP361 validation algorithm. In particular, $O_{\mathrm{payment}}$ is not a consensus field. Any real specification must decide how to classify outputs, including change, coinbase outputs, provably unspendable data outputs and novel witness programs. A node cannot infer a wallet's intent from the label "change".

## Example scenarios

| Transaction scenario | Research interpretation |
| --- | --- |
| Legacy input to an eligible PQ destination | Intended migration case |
| Legacy input with legacy payment and legacy change | Conflicts with the proposed destination restriction |
| Legacy input with PQ payment and legacy change | Change creates a new vulnerable output; requires policy redesign |
| PQ input to PQ output | Expected steady-state payment use case; exact rules need specification |
| PQ input to a legacy receiver | Inconsistent with the objective of ending new vulnerable outputs |
| Mixed inputs or unusual script types | Requires an explicit consensus classification rule |

A witness-version number alone does not establish security. For example a P2MR commitment might contain only classical signature leaves or an independently sufficient classical fallback. The eligibility rule would need a defensible relationship to the properties the network wants to enforce, while respecting the fact that committed scripts may be hidden.

## Economic and wallet effects

A deadline can increase incentives to upgrade before it becomes necessary. It may also concentrate demand near the deadline. Wallets need to generate safe change, avoid unsupported destinations and coordinate multi-party signing. Users relying on old hardware or pre-signed transactions may encounter incompatible policies. Merchants and exchanges must coordinate deposit and withdrawal changes rather than upgrading only their send path.

## Evidence needed before evaluation

- A normative output eligibility predicate and complete treatment of exceptions.
- Compatibility analysis for existing wallet, contract and payment protocols.
- A migration-demand model accounting for adoption delays and low-value UTXOs.
- A plan for deployment, rollback of software versions and chain reorganizations near the activation boundary.
