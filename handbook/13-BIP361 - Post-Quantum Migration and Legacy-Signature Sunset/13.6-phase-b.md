# 13.6 Phase B — Legacy-signature sunset

## Distinguishing restriction from confiscation or automatic migration

In the pinned canonical draft, Phase B tightens verification of legacy ECDSA and Schnorr authorization and envisages additional quantum-safe rescue conditions. It is described as a pre-announced flag-day at a predetermined block height, approximately two years after Phase A. The draft does not define the exact new proof predicate or how it is encoded and verified for all legacy script types.

A sunset would alter spendability, not rewrite the historical transaction that created an output. It does not automatically transfer balances to their owners' new wallets, miners or the state. If no permitted path can be satisfied, the output may remain unspendable under the new rules. That outcome is central to the governance debate.

## Why ordinary legacy verification is insufficient after compromise

For a conventional signature, a verifier checks whether the signature authenticates a transaction message under the public key. If an adversary has recovered the matching private scalar, valid signatures no longer distinguish the adversary from the original holder. Enforcing a stronger encoding rule or requiring a different sighash type would not restore the missing ownership distinction. An illustrative stricter rule might require both a legacy signature and evidence of an independent secret:

$$V_{\mathrm{new}}(tx,i)=V_{\mathrm{legacy}}(tx,i)\land R(tx,i,\pi).$$

Here $R$ is an unspecified rescue predicate and $\pi$ denotes proof data. This is a conceptual example of restriction, not a consensus rule supplied by BIP361. If $R$ can be satisfied using only the recovered private scalar, it does not add the desired security. If $R$ requires information never possessed by a legitimate owner, that owner may be unable to spend.

## Soft-fork reasoning

A tightening of consensus rules should make new valid spends a subset of previously valid spends, assuming compatibility of any additional data and validation path. For a candidate rule, one must show this property for actual transactions and script contexts, not just for the abstract conjunction above. Legacy nodes would not enforce the new predicate and could accept a block rejected by upgraded nodes. Miners and validating users therefore need coordinated software support.

A flag-day specifies when enforcement changes; it does not by itself specify the deployment mechanism, signaling threshold or readiness criteria. Do not import those details from another revision of the proposal. Mempool handling of transactions crossing the boundary also requires explicit policy design.

## Practical categories

| Holder situation | Possible consequence of a stronger rule |
| --- | --- |
| Migrated before the sunset | Legacy input restriction no longer applies to that migrated UTXO |
| Still controls legacy key and appropriate independent secret | May qualify for a future rescue mechanism |
| Has only the legacy scalar | Could lose access if no compatible rescue path exists |
| Key irretrievably lost | No ordinary authorization or independent recovery evidence may be available |
| Attacker with recovered scalar | Should not qualify for a secure rescue proof based on unavailable evidence |

These are conceptual outcomes, not current transaction validity decisions. BIP361 does not demonstrate universal recovery coverage.
