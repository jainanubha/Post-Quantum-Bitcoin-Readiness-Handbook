# 12.2 Evolution of BIP360

BIP360 is a draft specification whose design has changed substantially since its original publication. Historical articles may describe a different witness version, name, signature suite or commitment structure. This chapter uses version 0.12.1 as recorded in the canonical BIPs repository at commit `e7263a4cfe500c89e4269889244606953691ca33` (August 3, 2026).

## Selected milestones

| Date | Version | Design significance |
|---|---|---|
| 2024-09-27 | 0.1.0 | Initial proposal |
| 2024-12-18 | 0.5.1 | BIP number assigned |
| 2025-03-18 | 0.7.0 | Commitment and attestation design revised |
| 2025-07-07 | 0.8.0 | Reoriented toward Taproot without the vulnerable key path; future PQ validation via opcode or leaf-version mechanisms |
| 2025-07-20 | 0.9.0 | Witness version changed from 3 to 2 |
| 2025-09-17 | 0.10.0 | Renamed from Pay-to-Quantum-Resistant-Hash (P2QRH) to Pay-to-Tapscript-Hash (P2TSH) |
| 2026-02-10 | 0.11.0 | Renamed to Pay-to-Merkle-Root (P2MR) |
| 2026-06-18 | 0.12.0 | Depth-zero trees changed to succeed without evaluating their leaf script |
| 2026-07-24 | 0.12.1 | Reference construction code and test-vector updates |
| 2026-08-03 | 0.12.1, later commit | Witness-size comparison corrected, including CompactSize boundary |

## Design direction

The evolution illustrates a narrowing of scope. Rather than coupling an output format to a specific collection of post-quantum signatures, the current design reuses Taproot's tree hashing and Tapscript framework while removing the exposed output key and its direct spending route. The signature-selection question remains open. This separation reduces the number of decisions made by one proposal, although eventual deployment would still need coherent choices for validation, relay, wallet support and migration. The change to depth-zero trees is especially important. A single-leaf tree may still yield a 32-byte commitment, but under this revision a matching depth-zero proof succeeds without enforcing its script. An example written for an older revision may therefore be unsuitable for explaining the current proposed rules. Wallet designs must not treat a depth-zero P2MR tree as an ordinary authenticated spending policy.
