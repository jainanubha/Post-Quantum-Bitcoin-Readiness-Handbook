# 12.4 P2MR output construction

## Tagged hashes and the script tree

P2MR reuses the BIP341 script-tree hash construction. For a tag $T$, define

$$
H_T(x)=\mathrm{SHA256}(\mathrm{SHA256}(T)\parallel\mathrm{SHA256}(T)\parallel x).
$$

Here $T$ is the tag encoded as bytes. This domain separation distinguishes leaf hashes from branch hashes even when other input bytes overlap. For a script $s$ and one-byte leaf version $v$,

$$
L(s,v)=H_{\mathrm{TapLeaf}}(v\parallel\operatorname{CompactSize}(|s|)\parallel s).
$$

For two 32-byte node hashes $a,b$, the branch commitment is

$$
B(a,b)=H_{\mathrm{TapBranch}}(\min(a,b)\parallel\max(a,b)),
$$

where the ordering is lexicographic over bytes. Sorting is local to each branch, not a sort of all leaves. Tree grouping still matters: $B(B(a,b),c)$ need not equal $B(a,B(b,c))$.

## A two-leaf example

Let $s_A$ represent a normal spending policy and $s_B$ a recovery policy. For current Tapscript leaf version `0xc0`, compute $a=L(s_A,0xc0)$ and $b=L(s_B,0xc0)$. The root $r=B(a,b)$ is the witness program. No elliptic-curve point or tweaking step is needed to construct this output. The scripts themselves may contain public keys, timelocks or other supported conditions.

The proof for leaf $A$ consists of the sibling hash $b$; for leaf $B$ it consists of $a$. The proof reveals neither the text of the other script nor its internal structure. It does reveal the path depth, and low-entropy hidden scripts may be guessed and checked against their hashes.

## Output serialization and address representation

The draft specifies a native SegWit version-2 output with a 32-byte program. Its scriptPubKey bytes are represented as

`OP_2 OP_PUSHBYTES_32 <32-byte Merkle root>`

The two leading bytes are `52 20` in hexadecimal, followed by the root. The script is 34 bytes. A serialized transaction output additionally contains the 8-byte amount and a 1-byte CompactSize script length, giving 43 bytes under ordinary serialization.

Under BIP350, a witness version greater than zero uses Bech32m. Version 2 maps to the character `z` after the mainnet human-readable part and separator, yielding the `bc1z` prefix. This prefix identifies an address encoding, not proof of the presence of enforced P2MR validation.

## Construction safeguards

- An intended enforceable leaf should have depth at least one. A matching depth-zero proof bypasses script evaluation in the reviewed draft.
- Avoid branches whose satisfaction or future-version behavior grants unintended unconditional spending.
- Preserve exact script bytes, versions and tree grouping for backup and reconstruction.
- Treat key exposure and entropy of hidden policies separately from the root commitment.

The output root alone does not encode the wallet's complete policy in a recoverable form. Backup and descriptor design must retain enough information to reconstruct each intended spending path.
