# 12.6 Proposed consensus validation

## Scope of the proposed rules

BIP360 defines validation for native SegWit version-2 outputs with a 32-byte program. The following is an explanatory restatement of the reviewed draft; it is not executable consensus code. Other witness programs are outside this specific definition. All ordinary transaction-level validity requirements continue to matter.

## Validation sequence

1. Require at least two witness elements. If exactly two are present and the last begins with `0x50`, reject. With at least three elements, remove the last element as an annex if its first byte is `0x50`.
2. Require that at least the script and control block remain. Identify the penultimate item as the script and the final item as the control block.
3. Check that the control block length is $1+32d$ for an integer $0\le d\le128$. Check that the low bit of its first byte equals one. The leaf version is obtained by masking that byte with `0xfe`.
4. Compute the TapLeaf hash using the leaf version, CompactSize script length and script bytes. Process each sibling hash in order using the lexicographically sorted TapBranch construction.
5. Compare the reconstructed root to the 32-byte program. A mismatch fails validation.
6. If $d=0$, the proposed rule succeeds at this point without executing the leaf script.
7. Otherwise apply the leaf-version-dependent semantics. For version `0xc0`, execute under BIP342 rules, using the remaining witness arguments as the initial stack. Future leaf versions are presently treated as successful after the commitment checks, subject to any future restrictions.

The depth-zero rule is not equivalent to allowing an arbitrary witness to spend any output. The root commitment must first match. Nevertheless a matching proof reveals a path that does not enforce the script, so a wallet must never treat such a path as protected by its signature or timelock. The same general caution applies to future-version success semantics and `OP_SUCCESSx` leaves before a corresponding restriction is deployed.

## Ordinary Tapscript rules

For an enforced `0xc0` leaf without an early-success opcode, BIP342 supplies the script semantics. These include Schnorr signature validation, `OP_CHECKSIGADD`, disabled `OP_CHECKMULTISIG` operations, consensus MINIMALIF, resource limits on the initial stack and stack elements, and a signature-operation budget based on witness size. BIP360 references BIP342's signature-message extension, including the leaf hash and code-separator position. Merely replacing the key bytes inside an existing `OP_CHECKSIG` script does not introduce a new signature algorithm.

## Review cases

| Case | Expected result under reviewed proposal, assuming other transaction rules pass |
|---|---|
| One witness item | Fail; no key path |
| Invalid control-block length | Fail |
| Depth greater than 128 | Fail |
| Low control-byte bit zero | Fail |
| Incorrect sibling or script changes reconstructed root | Fail |
| Matching depth-zero proof | Succeed without script execution |
| Depth-one current-version leaf with invalid required signature | Fail, absent an applicable early-success rule |
| Depth-one current-version leaf with satisfied script | Succeed |
| Matching proof for future leaf version | Success under current proposed semantics, not a usable new signature type |

The normative specification and later consensus review must resolve precise edge conditions, including malformed/empty witness items, error handling and interaction with existing policy. The canonical text refers to the first byte of the last item; implementations need safe handling for empty items rather than out-of-bounds reads.

## Deployment distinction

Nodes without the proposed rules do not enforce P2MR authorization for witness version 2. A soft fork would restrict the set of accepted transactions for upgraded validators; relay policy and wallet recognition are separate concerns. A reference implementation and test vectors are valuable review material but do not indicate activation.
