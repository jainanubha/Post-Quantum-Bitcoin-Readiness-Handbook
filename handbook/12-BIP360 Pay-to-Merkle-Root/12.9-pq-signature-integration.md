# 12.10 Future post-quantum signature integration

## Output commitment versus signature semantics

An output format determines how spending conditions are committed to and revealed. A signature scheme determines how a message is authorized under a public key. BIP360 changes the first component while leaving new post-quantum signature semantics outside its specification. A P2MR leaf containing ordinary Schnorr checks is still an elliptic-curve authorization policy. The proposal retains Tapscript's extensibility, which can provide potential places to specify future verification behavior. Extensibility is not the same as a presently enforceable PQ mechanism. Any new behavior would need an independently reviewed consensus specification and activation.

## Candidate integration approaches

| Approach | Research question |
|---|---|
| New opcode | How are signature/key inputs represented, validated and resource-accounted? |
| New public-key type | How are encodings distinguished, and how can existing stack limits be accommodated? |
| New leaf version | Can a separate scripting or authorization language define precise semantics? |
| Separate witness version | Would a direct PQ authorization construction have different privacy and weight trade-offs? |
| Hybrid leaf policy | Can classical and PQ checks be bound to the same authorized transaction without downgrade paths? |

BIP342's `OP_SUCCESSx` mechanism allows future soft forks to impose new restrictions, including changes to some resource limits. Unknown public-key types and future leaf versions likewise have upgrade semantics, not secure default signature verification. A wallet must never fund a script depending on an unactivated verification rule for security.

## Requirements carried forward from Chapter 10

The 520-byte limit on ordinary Tapscript stack elements makes direct representation of many standardized PQ signatures problematic. ML-DSA and SLH-DSA signatures commonly exceed that size. A future integration must define how larger objects are presented, how resource limits apply and how malformed or noncanonical encodings are handled. Simply splitting a byte string across elements does not create a verifier or define its consensus semantics.

A new scheme must also specify the exact signing message and domain separation, signature and key encodings, permitted sighash modes, error behavior, validation budgets and interoperability test vectors. Node verification needs deterministic agreement on acceptance; signing devices have distinct randomness, state and side-channel requirements. The weight and fee model from Chapter 11 must be recalculated for the concrete format.

## Hybrid and fallback policies

Consider a future leaf requiring both a classical and a PQ signature. If the combination is correctly specified and both checks are required, breaking the classical signature alone need not authorize a spend. A different tree with one independently usable classical leaf and one PQ leaf does not have the same property. The attacker may choose the weakest sufficient path. A timelocked fallback changes which paths are available over time but is not automatically quantum-resistant.

Stateful and one-time hash-based schemes require particular attention to signing retries, backups and duplicated device state. The one-spend property of an output does not bound the number of signatures a wallet may generate. Any limited-use design must therefore be analysed in the context of actual wallet operations.
