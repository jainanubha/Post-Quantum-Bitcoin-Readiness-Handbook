# 12.11 Wallet and ecosystem implications

## From a valid output to a usable wallet

If BIP360 were activated, an interoperable P2MR wallet would need more than an address encoder. It would need a policy builder, script-tree construction and proof generation, signature-message support, transaction-size estimation, backup and restoration, and safe handling of unsupported leaf versions.

| Component | Prospective requirement |
|---|---|
| Address handling | Recognize the intended witness version and network; validate Bech32m checksum and length |
| Policy construction | Build enforced leaves at positive depth; reject unintended unconditional paths |
| Key management | Avoid exposing or reusing classical leaf keys unnecessarily |
| Backup | Preserve scripts, leaf versions, tree structure and derivation information |
| Signing | Reconstruct exact leaf commitment, sighash inputs and witness data |
| Fee estimation | Include chosen path depth, stack arguments and serialization overhead |
| Watch-only wallet | Balance policy discovery against leakage of key and tree data |
| Hardware signer | Review destination, amounts, spending policy and exact authorization context |

## Migration of existing policies

A Taproot script tree can serve as a conceptual starting point for a P2MR policy, but copying it verbatim may not be safe. A depth-zero tree needs redesign. A wallet that currently relies on a direct key path must express its intended authorization in an enforced leaf instead. Any additional leaves must be evaluated for unintended spending and recovery implications.

For example, a wallet might design a cooperative leaf and a time-delayed recovery leaf. Its backups must contain enough information to recreate the precise script tree and all necessary sibling hashes. Keeping only a seed may be insufficient if the tree construction or recovery policy cannot be reconstructed from that seed. A valid root is a commitment, not a compressed backup of the scripts.

Migration requires spending the original output under its current authorization rules and creating a new output. It does not convert the original UTXO in place. Funds with previously exposed keys remain exposed until successfully spent under the existing rules. Chapter 13 considers coordination and legacy-output policy separately.

## Compatibility and deployment

BIP350 allows future witness versions to be encoded using Bech32m, but encoding support is not equivalent to receiving, signing, validating or relaying that version. Older nodes may treat unrecognized witness programs as unrestricted under their consensus rules and may not relay such transactions under their policy. Wallets should not advertise secure P2MR receiving until the relevant rules and software support are available.

Exchanges, custodians and hardware manufacturers would need explicit support for deposit recognition, withdrawals, signing and recovery. Existing PSBT and descriptor conventions for Taproot do not automatically define P2MR-specific metadata. New interoperable conventions may be needed.

## Operational review checklist (future implementation)

- Can every intended path be reconstructed from a tested backup?
- Does the wallet reject unsafe depth-zero or early-success constructions?
- Are address/version support and activation checked independently?
- Can fee estimation handle alternative leaf depths and stack sizes?
- Can external signers verify the transaction and policy they are authorizing?
