# 12.5 P2MR spending mechanism

## Witness components

A P2MR input, under the draft rules, has no key-path case. Its witness carries the initial stack arguments followed by the selected leaf script and its control block, with an optional annex as the final item. The witness is serialized as a CompactSize item count, then a CompactSize length and the bytes of each item. The initial stack is not the entire serialized witness: the script, proof and annex are interpreted separately. For a leaf of depth $d$, the control block is a byte $c_0$ followed by $d$ consecutive 32-byte sibling hashes. Its length is

$$
C_{\mathrm{MR}}(d)=1+32d.
$$

The low bit of $c_0$ is required to be one. The upper seven bits identify the leaf version when the low bit is masked out. For the defined Tapscript version `0xc0`, the control byte is therefore `0xc1`. The low bit is a fixed encoding constraint in P2MR, not a parity check on an elliptic-curve output point.

## Illustrative ordinary signature leaf

Consider the conceptual leaf script `<32-byte x-only key> OP_CHECKSIG`, which occupies 34 bytes. Assume the leaf has depth one and uses the current BIP340 Schnorr signature semantics. The witness contains three items (without an annex):

| Item | Raw bytes | Meaning |
|---|---:|---|
| Signature | 64 | BIP340 signature using the default sighash type |
| Leaf script | 34 | Push key and verify signature |
| Control block | 33 | `0xc1` followed by the sibling hash |

The serialized per-input witness is 135 bytes: one item-count byte, three length prefixes and 131 bytes of payload. This excludes the transaction-level SegWit marker and flag, which are counted once per transaction. An explicit non-default sighash type adds one byte to the signature item in this example.

The example shows that a P2MR output can initially rely on a classical signature inside a hidden script. Such a spend is not post-quantum secure against an attacker capable of recovering the newly revealed key within the unconfirmed transaction window. It is also conditional on the key not having been exposed earlier.

## Reconstructing the path

The verifier computes the leaf hash from the actual script bytes and leaf version. Starting at that hash, it combines the successive sibling hashes in the order provided by the control block, sorting each pair before applying TapBranch. If the resulting root differs from the output program, the witness fails. Otherwise the depth and leaf version determine whether script execution is required.

A valid Merkle proof is evidence that a script was committed to, not that its spending conditions have been satisfied. This distinction is essential because the reviewed BIP intentionally permits depth-zero proof success without evaluation. For normal enforced Tapscript leaves, the script must additionally succeed with its initial stack arguments.

## Annex and signature binding

The optional annex is recognized according to the proposal's witness parsing rules and begins with byte `0x50`. It is not a script argument. Where a signature is evaluated, the BIP341/342 signature-message construction commits to annex presence and contents. Annex bytes contribute to witness serialization and weight.
