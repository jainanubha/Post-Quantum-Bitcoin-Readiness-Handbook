# 11.7 Worked transaction-weight and fee examples

This section applies the M1 model to standardized signatures and compares it with the current P2TR key-path baseline. All cases have two 34-byte output scripts and use default-sighash Schnorr or the raw encoded PQ signature with no additional mode byte. The hypothetical inputs are independent; there is no key sharing or aggregation. The Falcon row uses the padded candidate format rather than a finalized standard. All PQ results are hypothetical size estimates.

## Example 1 — one input and two outputs

For the baseline, $B=137$, $D=68$, $W=616$ and $v=154$. For ML-DSA-44, $D=2+3739=3741$, so

$$
W=4(137)+3741=4289,\qquad v=\lceil4289/4\rceil=1073.
$$

At 10 sat/vB the target fee is 10,730 sat, approximately 6.97 times the baseline's 1,540 sat. The raw signature ratio of 37.8 is not the transaction fee ratio, because the baseline includes fixed fields and witness bytes receive different accounting.

For SLH-DSA-128s, $D=2+7893=7895$, $W=8443$ and $v=2111$. At the same fee rate the target fee is 21,110 sat, approximately 13.71 times the baseline. The small SLH-DSA public key does not compensate for its much larger signature in this particular model.

| ML-DSA-44 | 137 | 3,741 | 3,878 | 4,289 | 1,073 | 10,730 |

## Example 2 — five inputs and two outputs

The stripped size is now $10+41(5)+43(2)=301$ B. The shared marker and flag remain two bytes. Under M1, each input independently includes a key and signature. For ML-DSA-44, the witness delta is $2+5(3739)=18,697$ B; weight is $4(301)+18,697=19,901$ WU and vsize is 4,976 vB.

| Input authorization | Base (B) | Witness delta (B) | Total (B) | Weight (WU) | Virtual size (vB) | Fee at 10 sat/vB (sat) |
| --- | --- | --- | --- | --- | --- | --- |
| P2TR key path | 301 | 332 | 633 | 1,536 | 384 | 3,840 |
| ML-DSA-44 | 301 | 18,697 | 18,998 | 19,901 | 4,976 | 49,760 |
| ML-DSA-65 | 301 | 26,342 | 26,643 | 27,546 | 6,887 | 68,870 |
| ML-DSA-87 | 301 | 36,132 | 36,433 | 37,336 | 9,334 | 93,340 |
| SLH-DSA-128s | 301 | 39,467 | 39,768 | 40,671 | 10,168 | 101,680 |
| SLH-DSA-128f | 301 | 85,627 | 85,928 | 86,831 | 21,708 | 217,080 |
| Falcon-512 padded candidate | 301 | 7,852 | 8,153 | 9,056 | 2,264 | 22,640 |

As input count increases, the per-input authorization overhead becomes a greater fraction of the transaction. The difference between schemes grows in absolute terms; ratios are sensitive to the number of outputs and the baseline chosen.

## Example 3 — one illustrative script-proof variation

Suppose an M1-like future construction instead adds two witness items: a 34-byte script and a 65-byte proof. They add $(1+34)+(1+65)=101$ bytes when the vector's count remains under 253. The ML-DSA-44 model's weight becomes 4,390 WU, or 1,098 vB. This example is only a sensitivity test for additional serialized objects. Neither the script nor the proof is claimed to be a valid PQ script or a P2MR proof.

## Example 4 — hybrid authorization

Suppose M4 requires a 64-byte classical signature and a 32-byte classical public key in addition to the M1 ML-DSA-44 items. The classical items add 98 bytes, and the vector count stays one byte. The hypothetical weight becomes 4,387 WU and the virtual size 1,097 vB. The additional authorization is relatively small in size terms, but changes key management, validation and the security policy. If a real design encodes classical keys or signatures elsewhere, the calculation changes.

## Reproducibility

The [scenario comparison table](../../tables/pq-transaction-weight-comparison.md) records all parameter inputs and calculated results. Recompute any row by applying the CompactSize rule, summing base and witness bytes, then rounding once at transaction level. Do not interpret these estimates as measurements of verification speed or actual mined transactions.
