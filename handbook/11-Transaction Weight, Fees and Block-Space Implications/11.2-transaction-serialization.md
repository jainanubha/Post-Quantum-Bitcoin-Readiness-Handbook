# 11.2 Bitcoin transaction serialization

The unit of analysis is the serialized transaction, not an abstract signature. Each byte must be attributed to either the stripped serialization or the additional witness serialization. This section defines the quantities used throughout the chapter.

## Stripped transaction fields

For a non-coinbase transaction, the stripped form contains the version, input count, inputs, output count, outputs and locktime. A transaction input contains an outpoint (32-byte transaction hash and 4-byte index), a length-prefixed `scriptSig` and a 4-byte sequence. An output contains an 8-byte value and a length-prefixed `scriptPubKey`.

| Field | Length (bytes) |
| --- | ---: |
| Version | 4 |
| Input count | CompactSize |
| Each outpoint | 36 |
| Each scriptSig | CompactSize length + script bytes |
| Each sequence | 4 |
| Output count | CompactSize |
| Each output value | 8 |
| Each scriptPubKey | CompactSize length + script bytes |
| Locktime | 4 |

If $n$ and $m$ are input and output counts, $a_i$ is the length of input $i$'s scriptSig, $b_j$ is the length of output $j$'s scriptPubKey, and $c(x)$ is the CompactSize length function, then

$$
B=8+c(n)+c(m)+\sum_{i=1}^{n}(40+c(a_i)+a_i)+\sum_{j=1}^{m}(8+c(b_j)+b_j).
$$

A native SegWit input normally has an empty scriptSig, giving 41 stripped bytes. An output with a 34-byte scriptPubKey (e.g. P2TR or P2WSH) occupies 43 bytes including its amount and length field. A P2WPKH output has a 22-byte scriptPubKey and occupies 31 bytes. These are output serialization lengths, not the cost of later spending them.

## CompactSize integers

| Integer value | Encoded length |
| --- | ---: |
| 0–252 | 1 B |
| 253–65,535 | 3 B |
| 65,536–4,294,967,295 | 5 B |
| 4,294,967,296–2^64−1 | 9 B |

CompactSize prefixes are not Script push opcodes. Witness items use CompactSize lengths; a legacy scriptSig uses Script data pushes inside an outer CompactSize-prefixed script.

## Witness serialization

For a transaction using witness serialization, the marker and flag add two bytes after the version. Each input has a witness vector, including a zero-item vector for an input without witness data in a mixed transaction. If input $i$ has $k_i$ witness items of lengths $l_{i,j}$, the additional serialization is

$$
D=2+\sum_{i=1}^{n}\left[c(k_i)+\sum_{j=1}^{k_i}(c(l_{i,j})+l_{i,j})\right].
$$

The total serialized size is $T=B+D$. For a transaction with no witness serialization, $D=0$. Do not add marker and flag or empty vectors in that case. For example, a key-path Taproot witness with one 64-byte signature occupies $1+1+64=66$ bytes before the shared marker and flag.

## Commitments and exposure

Output design determines which information resides in the UTXO set and which is revealed in the spending transaction. A compact commitment can defer the cost of a large public key until spending; it does not eliminate that cost. A script-path construction may additionally reveal the executed script and authentication proof. These bytes must be counted wherever the selected rules place them.
