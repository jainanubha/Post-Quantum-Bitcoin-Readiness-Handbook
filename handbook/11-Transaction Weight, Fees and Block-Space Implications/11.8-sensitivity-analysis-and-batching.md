# 11.8 Sensitivity analysis and batching

The results in Section 11.7 are conditional on the selected input and output counts. Sensitivity analysis changes one assumption at a time to reveal which factors have the greatest effect on costs.

## Marginal input and output weights

While count encodings remain unchanged, a native witness input with an empty scriptSig contributes 164 WU in stripped data plus its serialized witness vector. The shared marker and flag are excluded from marginal input weight, assuming the transaction already uses witness serialization.

| Input authorization | Witness vector (B) | Marginal input (WU) | Marginal weight / 4 (vB, unrounded) |
| --- | --- | --- | --- |
| P2TR key path | 66 | 230 | 57.50 |
| ML-DSA-44 | 3,739 | 3,903 | 975.75 |
| ML-DSA-65 | 5,268 | 5,432 | 1,358.00 |
| ML-DSA-87 | 7,226 | 7,390 | 1,847.50 |
| SLH-DSA-128s | 7,893 | 8,057 | 2,014.25 |
| SLH-DSA-128f | 17,125 | 17,289 | 4,322.25 |
| Falcon-512 padded candidate | 1,570 | 1,734 | 433.50 |

A 34-byte output script contributes 43 stripped bytes, or 172 WU. Its marginal fee is therefore 43 times the fee rate, assuming no other field changes. For ML-DSA-44, the marginal input cost is 3,903 WU, equivalent to 975.75 unrounded vB. The difference in rounded transaction vsize can depend on the original transaction's weight remainder.

## Input-count sensitivity

Hold the output count at two and fee rate at 10 sat/vB.

| Inputs | P2TR vB | ML-DSA-44 vB | SLH-DSA-128s vB | ML-DSA-44 fee (sat) | SLH-DSA-128s fee (sat) |
| --- | --- | --- | --- | --- | --- |
| 1 | 154 | 1,073 | 2,111 | 10,730 | 21,110 |
| 2 | 212 | 2,048 | 4,125 | 20,480 | 41,250 |
| 5 | 384 | 4,976 | 10,168 | 49,760 | 101,680 |
| 10 | 672 | 9,854 | 20,239 | 98,540 | 202,390 |
| 20 | 1,247 | 19,612 | 40,382 | 196,120 | 403,820 |

At a fixed fee rate, fees scale with virtual size; increasing the rate scales the cost of each design almost linearly (subject to integer rounding). If a fee rate is endogenous to a congested market, these fixed-rate comparisons no longer predict the actual price of confirmation.

## Batching payments

Assume five independent payments are each represented by one input, one recipient output and one change output. Compare that with a single transaction using the same five inputs, five recipient outputs and one change output. No signature aggregation occurs; the savings come from shared transaction overhead and fewer change outputs. Each output has a 34-byte script.

| Input authorization | 5 separate txs (total vB) | 1 batched tx (vB) | Savings (vB) | Savings (%) |
| --- | --- | --- | --- | --- |
| P2TR key path | 770 | 556 | 214 | 27.79% |
| ML-DSA-44 | 5,365 | 5,148 | 217 | 4.04% |
| SLH-DSA-128s | 10,555 | 10,340 | 215 | 2.04% |

The absolute savings are similar because the removed outputs and transaction overhead are the same, while relative savings shrink as signatures dominate. Real wallets may use different input counts, coin selection and change behavior. Batching also creates linkability between payments and can complicate replacement or confirmation of individual payments. It is not a universally optimal strategy.

## Additional sensitivity axes

A later analysis should vary output length, script/proof length, signature encoding, mixed input types, count-prefix boundaries, signature sharing where supported, and verifier resource pricing. Separate the effect of changing the primitive from the effect of changing the spending construction.
