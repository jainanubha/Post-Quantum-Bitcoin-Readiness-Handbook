# 11.11 Transaction-weight and fee estimator design

This section provides a mathematical specification and acceptance examples without implementing the tool. The future estimator should distinguish real classical templates from hypothetical PQ models.

## Inputs

| Input | Meaning | Validation |
| --- | --- | --- |
| Input list | Each input's scriptSig length and witness item lengths | Nonnegative integer byte lengths; at least one input |
| Output list | Each output's scriptPubKey length | Nonnegative integer byte lengths; at least one output |
| Witness serialization | Whether marker, flag and input vectors are present | No witness serialization for entirely empty witness data; native templates require witnesses |
| Fee rate | Target fee in sat/vB | Finite nonnegative value, with explicit decimal precision |
| Authorization template | Classical or hypothetical PQ profile | Named, versioned, with source and status |
| Available block-weight budget | Optional scenario parameter | Positive integer no greater than the assumed consensus block limit |

## Calculation contract

1. Calculate CompactSize lengths for the input count, output count, script lengths and witness vectors.
2. Sum stripped fields using the Section 11.2 formula. For mixed input types, count each scriptSig independently.
3. If witness serialization is present, count marker and flag exactly once and the witness vector for every input, including zero-item vectors for non-witness inputs.
4. Calculate total serialized bytes, weight and virtual size. Round virtual size only once.
5. Apply the chosen fee rate to the rounded virtual size and round the target fee up to the next satoshi. If values are provided, compute actual fee separately and compare with target.
6. If requested, report weight-only capacity using the floor of available budget divided by transaction weight. Do not infer confirmation probability.
7. Report assumptions, warnings, and source links alongside results. Flag current policy and consensus constraints separately; the calculator does not implement script validation.

## Expected outputs

Return stripped size, witness delta, total size, weight, BIP141 vsize, size-based target fee, optional realized fee rate, optional marginal costs and weight-only capacity. If comparing designs, return absolute differences and ratios with their denominator explicitly identified.

## Acceptance examples

| Case | Stripped (B) | Witness delta (B) | Weight (WU) | vsize (vB) | Fee at 10 sat/vB |
| --- | ---: | ---: | ---: | ---: | ---: |
| Legacy P2PKH, 1 in/2 out, 107-byte scriptSig | 244 | 0 | 976 | 244 | 2,440 |
| P2WPKH, 1 in/2 out, witness [72,33] | 137 | 110 | 658 | 165 | 1,650 |
| P2TR, 1 in/2 out, witness [64] | 137 | 68 | 616 | 154 | 1,540 |
| P2TR, 1 in/2 out, witness [65] | 137 | 69 | 617 | 155 | 1,550 |
| M1 ML-DSA-44, 1 in/2 out | 137 | 3,741 | 4,289 | 1,073 | 10,730 |
| M1 SLH-DSA-128s, 1 in/2 out | 137 | 7,895 | 8,443 | 2,111 | 21,110 |
| M1 ML-DSA-44, 5 in/2 out | 301 | 18,697 | 19,901 | 4,976 | 49,760 |

All outputs use 34-byte scripts and no annex unless stated. Include boundary tests for lengths 252/253 and 65,535/65,536, count boundaries, zero-length witness items versus a zero-item vector, mixed witness/non-witness inputs, invalid negative lengths, and fractional fee rates. For example, at 1.25 sat/vB a 154-vB transaction has a target fee of 193 sat.

Later testing should compare valid classical templates with serialized transactions decoded by Bitcoin Core (size, weight and vsize), using controlled fixtures. Hypothetical formats are checked arithmetically rather than broadcast or treated as valid Bitcoin transactions. The static [scenario table](../../tables/pq-transaction-weight-comparison.md) and [fee sensitivity table](../../tables/pq-fee-sensitivity.md) are initial reference fixtures.
